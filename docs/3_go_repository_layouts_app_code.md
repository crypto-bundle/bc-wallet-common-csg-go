# Код приложения. Правила организации кода

## Введение

В данном документе описаны правила регламентирующие организацию структуры директорий и файлов
внутри репозитория содержимое которых представляет из себя **програмный код целевого приложение**,
одного или нескольких.

В документе представлены рекомендации для языка программирования Go.

## Цели

Правила регламентирующие огранизацию файловую структуры для разработки на языке Go, решают следующие задачи:
- Ускорить работу над проектом для нового разработчика - 
  _"переход между разработкой разных приложений становится привычной задачей"_.
- Упростить и унифицировать компиляцию приложений - 
  одинаковая структура директорий упрощает создание скриптов компиляции приложений.

## Правила

За основу взяты базовые руководства из [golang-standards/project-layout](https://github.com/golang-standards/project-layout/blob/master/README_ru.md#%D0%B4%D0%B8%D1%80%D0%B5%D0%BA%D1%82%D0%BE%D1%80%D0%B8%D0%B8-go),
необходимо им следовать. Ниже приведены основные принципы:
- `/cmd` - Точки входа для компляции приложения `main.go` должны быть находиться 
  каждая в своей под-директории внутри директории `/cmd`, например:
  - `/cmd/api/main.go`
  - `/cmd/controller/main.go`
- Внутри пакета `main` может находиться только один `main.go` файл, другие файла создать не рекомендуется.
- `/internal` - Внутренний код приложения должен быть расположен в директории `/internal`. 
  Пакеты определенные в директории `internal` запрещено использовать 
  как экспортируемые сущности в других проектах
- `/pkg` - Код сущностей для которых предусмотрена возможность использования в сторонних проекта должен быть
  расположен в директории `/pkg`. Пакеты из этой директории разрешено использовать как экспортируемые для
  других проектов.
- `/vendor` - зависимости вашего Go-модуля должны храниться в директории `/vendor`.
- Версионирование зависимостей должно быть определено в файлах:
  - `go.mod`
  - `go.sum`

Внутри директории `/internal` так же необходимо соблюдать определенные ниже правила и рекомендации.
В частности необходимо соблюдать соглашение об обязательных директориях:
- `/internal/app`
- `/internal/entities` - здесь собраны все модели данных описанные в виде Go-структур
- `/internal/types` - здесь собраны все кастомные типы основанные на базовых типах данных,
  в основном это перечисляемые типы данных. Это могут быть объявленные типы данных для обозначения статус-кодов
  какой либо модели данных из пакета `entities`.
- `/internal/config` - здесь собраны все файлы в которых описаны Go-структуры отвечающие за конфигурацию приложения.
  Это различные сервис-компоненты которые внутри себя реализуют логику извлечения различных конфигурационных переменных
  из множества различных источников. Допустимые источники данных для конфигурации описаны в 
  документе [Конфигурационные файлы](./3_go_repository_layouts_config_files.md).
- `/internal/*_data` - здесь собраны различные сервис-компоненты отвечающие за работу слоя данных приложения.
  Важно понимать что это не одна конкретная директория, а множество возможных директорий с постфиксом `_data`
  в названии. Сервис-комноненты в таких пакетах могут обслуживать потребности в общении 
  с различными сервисами хранения данных, такие как:
  - PostgreSQL/MySQL/SQLite
  - Redis/DragonFlyDB
  Подробнее про организацию пакетов слоя данных можно почитать в [Application Data Layer](./4_go_app_data_layer.md).
- `/internal/processing` - данная директории располагаются файли и другие директории в которых содержаться различные
  сервис-компоненты отвечающие за асинхронный процессинг каких либо задач. Подробнее про механизм процессинга 
  можно прочитать здесь [Application Processing Mechanism](./4_go_app_processing.md).
