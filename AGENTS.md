# Руководство по написанию правил Code Style Guide (CSG)

## Overview

Этот документ описывает **единый шаблон** для всех файлов CSG внутри каталога `pkg/csg/docs/`. Он обязателен при создании новых документов и изменении существующих.

Модель: один логический раздел (`docs/<domain>/`) = один или несколько тематических Markdown-файлов; каждый файл = одна тема со своими правилами.

> **[Важно]** Файл `./pkg/csg/AGENTS.md` является **навигационным справочником** — он содержит краткие выжимки из правил и помогает ориентироваться в структуре Code Style Guide. В нём **не размещаются** рекомендации по написанию правил — они находятся только в этом документе.

## Обязательная структура файла

Каждый Markdown-файл CSG **обязан** содержать следующие элементы в строгом порядке:

### 1. YAML front-matter (meta-блок для MkDocs)

Блок в формате YAML размещается в самом верху файла между тройными дефисами. Его наличие обязательно для корректной индексации в MkDocs.

```yaml
---
title: Краткое название темы (до 60 символов)
description: Однострочное описание содержания (до 150 символов)
category: имя_категории_в_теге_или_разделе
tags: [tag1, tag2, tag3]
---
```

| Поле          | Обязательность | Описание                                          | Пример значения                    |
| ------------- | -------------- | ------------------------------------------------- | ---------------------------------- |
| `title`       | Да             | Отображаемое имя документа в боковой панели MkDocs | `Оформление функций`               |
| `description` | Да             | Короткое однострочное описание содержания         | `Правила сигнатур и тел функций`   |
| `category`    | Да             | Логическая категория для группировки в навигации  | `App Development`, `Architecture`  |
| `tags`        | Да             | Массив тегов для фильтрации и поиска              | `[functions, signatures, code-writing]` |

### 2. Аннотационный блок

Непосредственно после YAML front-matter размещается блок аннотации — краткая суть документа для быстрого чтения человеком (разработчиком или AI-агентом). Блок ограничен строками `---`.

```markdown
---
**Цель**: <Чётко сформулированная цель документа или правила>
**Категория правил**: <Общая категория и подкатегория>, <подкатегория>
**Краткое содержание:** <Одно-два предложения — о чём этот документ>
---
```

| Поле                 | Обязательность | Описание                                       |
| -------------------- | -------------- | ---------------------------------------------- |
| `Цель`               | Да             | Зачем существует этот документ / правило         |
| `Категория правил`   | Да             | Путь по дереву категорий CSG                    |
| `Краткое содержание` | Да             | Сухое резюме содержания                        |

### 3. Заголовок первого уровня (`# ...`)

Название документа, повторяющее или раскрывающее смысл `title` из YAML front-matter.

```markdown
# Оформление функций

## Введение (опционально)
```

### 4. Разделы (`## ...`)

Логические подразделы, группирующие правила по смыслу. Используйте заголовки второго уровня для разделения тем в рамках одного документа.

Пример:
```markdown
## Введение

Краткий вводный текст раздела. Объясняет контекст и назначение документа.

## Сигнатура функции

Раздел про правила оформления сигнатур.

## Тело функции

Раздел про правила оформления тела функции.
```

### 5. Правила (`### Правило N: <label>`)

Каждое правило — заголовок третьего уровня с нумерацией и подписью. Нумерация ведётся **внутри каждого раздела** (`## ...`), начиная с `1`.

**Шаблон заголовка правила:**

```markdown
### Правило 1: <краткое_название_правила>
```

**Правила именования `<label>`:**
- Используйте имена существительные или короткие фразы в именительном падеже.
- Максимум 5–7 слов.
- Избегайте предлогов и артиклей там, где можно опустить.

Хорошие примеры label:
- `Параметры на отдельных строках`
- `Запрет оператору goto`
- `Отступы между блоками кода`

Плохие примеры label:
- `Правило оформления параметров функции` (избыточно длинный)
- `о параметрах` (слишком коротко, не понятно контекст)
- `_private_label_` (некорректный casing)

### 6. Содержимое правила

Каждое правило **обязано** содержать:

1. **Описание** — текстовое объяснение правила. Один-три абзаца.
2. **Пример GOOD** — код, показывающий правильный подход.
3. **Пример BAD** — код, показывающий неправильный подход.

#### Шаблон содержимого правила

```markdown
### Правило N: <label>

<Описание правила: что требуется и почему>.

```go
// BAD: Неправильно — <краткое пояснение ошибки>
func BadExample() {
    // ошибочный код
}
```

```go
// GOOD: Правильно — <что делает правильно>
func GoodExample() {
    // корректный код
}
```
```

#### Правила оформления примеров:

| Элемент               | Требование                                                        |
| --------------------- | ----------------------------------------------------------------- |
| Тег `// BAD`          | **Всегда** размещайте комментарий `// BAD:` в начале блока кода с кратким пояснением |
| Тег `// GOOD`         | **Всегда** размещайте комментарий `// GOOD:` в начале блока кода с кратким пояснением |
| Имена функций         | Использовать осмысленные имена: `BadExample`, `GoodExample`, `ProcessOrder` |
| Контекст кода         | Приводить достаточно кода, чтобы пример был самодостаточным (imports, типы если нужно) |
| Комментарии внутри    | Краткие, на русском языке, объясняющие **почему** код плохой или хороший |
| Полнота                | Код должен быть компилируемым Go-кодом (валидные imports, корректный синтаксис) |

## Полный шаблон файла

Ниже — полный скелет документа, который можно использовать как шаблон для создания нового правила или группы правил.

```markdown
---
title: <Название темы до 60 символов>
description: <Однострочное описание до 150 символов>
category: <category-tag>
tags: [tag1, tag2, tag3]
---

---
**Цель**: <Цель документа>
**Категория правил**: <Category>, <Subcategory>
**Краткое содержание:** <Краткое резюме>
---

# <Название документа (уровень 1)>

## Введение

<Краткий вводный текст. Объясняет контекст и назначение документа. Опционально, но рекомендуется для понимания цели документа.>

## <Раздел 1>

<Вводный текст раздела (опционально).>

### Правило 1: <label>

<Описание правила. Объясняет суть требования и мотивацию.>

```go
// BAD: Неправильно — краткое пояснение, почему так делать нельзя
func badFunction(param string) error {
    // ошибочный код с комментариями
    return nil
}
```

```go
// GOOD: Правильно — краткое пояснение, почему так делать надо
func goodFunction(param string) error {
    // корректный код с комментариями
    return nil
}
```

### Правило 2: <label>

<Ещё одно правило по той же теме.>

```go
// BAD: ...
```

```go
// GOOD: ...
```

## <Раздел 2>

### Правило 1: <label>

Нумерация начинается заново в новом разделе `## ...`.

```go
// BAD: ...
```

```go
// GOOD: ...
```
```

## Поддержка вариантов сборки (build tags)

Все go-файлы внутри проекта `bc-wallet-common-csg-go` должны учитывать возможные варианты сборки и использовать соответствующие build-теги:

| Тег          | Описание                                       | Поведение CSGService                     |
| ------------ | ---------------------------------------------- | ---------------------------------------- |
| `development`| Полная функциональность, включая docs embedding | Сервис запускается, выводит справочники  |
| `staging`    | Сборка для тестирования                        | Полная работа CSGService не требуется     |
| `production` | Продакшен-сборка                               | Полная работа CSGService не требуется     |

Для разделения файлов по вариантам сборки применяйте директивы `//go:build` в начале файла:

```go
//go:build development

package main
```

При сборке без тега (`go build .`) файлы с `//go:build development` **не будут** включены в бинарник.

При сборке с нужным тегом (`go build -tags staging .`) активируются только файлы для этого варианта.

## Чеклист перед коммитом нового правила

Используйте этот чеклист при создании или изменении файлов CSG:

1. **YAML front-matter** присутствует и заполнен всеми обязательными полями?
2. **Аннотационный блок** (`---Цель---Категория---Краткое содержание---`) стоит сразу после YAML front-matter?
3. **Заголовок первого уровня** (`# ...`) идёт сразу после аннотации?
4. Разделы используют заголовки **второго уровня** (`## ...`)?
5. Каждое правило использует заголовок **третьего уровня** в формате `### Правило N: <label>`?
6. Нумерация правил (**N**) начинается с 1 в каждом разделе (`## ...`) и продолжается последовательно?
7. Каждое правило содержит **текстовое описание**?
8. Каждое правило содержит пример **BAD** с комментарием `// BAD:`?
9. Каждое правило содержит пример **GOOD** с комментарием `// GOOD:`?
10. Код-блоки используют тег ````go` (не generic `bash` или другой)?
11. Приведённый Go-код **синтаксически валиден** (нет незакрытых скобок, не компилируемых конструкций)?
12. Название документа не дублирует существующие файлы — проверьте через:
    ```bash
    glob pkg/csg/docs/**/*.md
    ```

## Навигация по существующим правилам

Все файлы CSG расположены в одном месте — `./pkg/csg/docs/`:

| Раздел                              | Содержание                                  |
| ------------------------------------ | ------------------------------------------- |
| `app-development/`                   | Архитектура приложения, ошибки, конфиг, DB  |
| `repository/`                        | Структура репозитория, CI/CD, линтеры         |
| `toolkit/`                           | Утилиты проекта: golangci-lint, migrator     |
| `setup/`                             | Настройка окружения                          |
| `processes/`                         | Процессы, периметры ответственности          |
| `diagrams/`                          | Диаграммы                                   |
| `examples/`                          | Примеры файлов (LICENSE, .env)               |

Полная карта навигации доступна в [`./pkg/csg/AGENTS.md`](./pkg/csg/AGENTS.md) — это навигационный справочник с ссылками на все документы.

## Сохранение планов работ

Когда работа требует планирования изменений (рефакторинг, добавление фичи, генерация CHANGELOG, релиз и т.д.) — **сначала создай план**, прежде чем приступать к реализации.

### Где хранить

Все файлы планов сохраняются в корневой директории:

```
.agents/plans/<NNN>_<short_plan_description>.md
```

- `<NNN>` — трёхзначный порядковый номер (`001`, `002`, …). Увеличивается при создании нового плана. Не сбрасывается между сессиями.
- `<short_plan_description>` — краткое описание на английском, snake_case, без пробелов. Примеры: `changelog-generation`, `release-v0-1-0`, `error-handler-refactor`.

### Когда создавать

- Перед многошаговыми задачами, затрагивающими более 2–3 файлов.
- При выполнении релизного процесса (версионирование, CHANGELOG, теги).
- При рефакторинге, затрагивающем архитектуру или публичные API.
- По требованию пользователя или когда сложность задачи явно превышает одно действие.

### Что включать в план

1. **Контекст** — краткое описание цели и области изменений.
2. **Шаги реализации** — пронумерованные подзадачи с указанием целевых файлов и ожидаемых результатов.
3. **Критерии приёмки** — что считается успешно завершённой задачей (линтинг, тесты, проверки).
4. **Ожидаемые риски** — потенциальные побочные эффекты или точки внимания.
5. **Опциональные варианты** — если есть альтернативные пути реализации.

### Конвенция именования файлов

| Элемент | Формат | Пример |
|---------|--------|--------|
| Порядковый номер | 3 знака, zero-padded | `001`, `002` |
| Описание | snake_case, lowercase | `changelog-generation`, `docs-embed-refactor` |
| Расширение | `.md` | всегда markdown |
| Разделитель | `<` | `-` между номером и описанием |

Правильные имена: `001_changelog-generation.md`, `042_error-handler-refactor.md`  
Неправильные: `plan-changelog.md`, `01 Changelog.md`, `Changelog_Generation_Md`

### Процесс

1. Создай план в `.agents/plans/<NNN>_<description>.md` с помощью `write_file`.
2. Представь план пользователю для согласования.
3. **Не исполняй план автоматически.** Жди явного подтверждения пользователя (или триггера `/continue`).
4. После выполнения отмет статус в плане или закомментируй выполненные шаги.

### Чистка

- Удалённые или отменённые планы можно архивировать в `.agents/plans/archive/` или удалять полностью.
- Архивирование предпочтительнее при наличии связанных коммитов или релизов.
