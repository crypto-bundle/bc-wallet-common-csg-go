# Написание кода. Правила оформления кода функций

---
**Цель**: Регламентировать правила и требования к написанию сервис-компонентов
**Категория правил**: App Development, code writing
**Краткое содержание:** Правила оформления программного кода для сервис-компонентов. Функции "создатели", передача зависимостей, экспортируемые и не экспортируемые.
---

## Введение

Сервис-компонент - это отдельная логическая часть программы, инкапсулирующая конкретную бизнес-логику или задачу. Примерами сервис-компонентов могут быть:
- Структура скрывающая в себе логику взаимодействия с базой данных с точки связаности (подключение, проверка наличия связы, переподключение)
- Структура скрывающая в себе логику взаимодействия с конкретными таблицами базы данных (компиляция SQL-запросов, вызовы SQL-кода, поучение и обработка данных)
- Структура исполняющая какую-то бизнес-логику но скрывающая внутри себя детали и конкретные алгоритмы работы
- Структура имеющая внутри себя логику работу фоновых асинхронных процессов

В проекте существуют определенные требования к оформлению сервис-компонентов, а так же к их жизненному циклу.

## Фактори функции

"Factory function" это функция содающая экземпляр той или иной Go-структуры которая обладает одной или несколькими "функциями-ресиверами". Иными словами - структура имеющая "методы", это уже сервис-компонент.

Заданы определенные правила на:
- оформления сигнатуры функции:
    - название функции
    - парядок передачи аргументов
    - возвратные параметры
- принятия решение о возможности ее экспортирования

### Правила название factory функции

1. Обязана начинаться с одного из ключевых слов - `Make`, `New`. Все остальное запрещено
1. Конец функции обязан заканчиваться на одного из ключевых слов - `Service`, `Worker`.
1. Название должно четко описывать задачу которую выполняет сервис-компонент
1. Название должно содержать в себе сокращенное название возвращаемой структуры с необходимым постфиксами для удобства чтения
1. Название оформляется строго в стиле "Cames Case"

Примеры:
- `func MakeDepositOrderProcessorService() (*depositOrderProcessor, error)`
- `func NewWithdrawOrderFraudCheckerService() (*withdrawFraudChecker, error)`
- `func NewBaseConfigService() (*baseConfig, error)`

## Реализация сервис-компонента

### Категриории зависимостей

- **Категория первого приоритета**: Служебные зависимости или "базовые"
    - **Описание**:  Сервис-компоненты обязательные с точки зрения архитектуры приложения. Это базовый набор сервис-компонентов с которым инициализируется любое приложение.
    - **Внутренний приоритет категории**:
        - экземпляр форматтера ошибок (если необходим)
        - экземпляр логгера (если необходим)
        - экземпляр сервис-компонента конфигурации (если необходим)
        - экземпляр трассироващика (если необходим, и если передается как отдельный сервис-компонент)

- **Категория второго приоритета**: Инфраструктурные
    - **Описание**: Зависимости внутренней инфраструктуры
    - **Внутренний приоритет категории**:
        - экземпляр подключения к менеджмеру секретов (например Hashicorp Vault)
        - экземпляр подключения к persistent storage (например postgresql, clickhouse)
        - экземпляр подключения к cache storage (например redis, keydb)
        - экземпляр подключения к брокеру очереде (например NATS, Kafka, Rabbit)
        - экземпляр клиента к обязательным удаленным API, но внутренним относительно проекта и компании
        - и тому подобное ...

- **Категория третьего приоритета**: Логические зависимости
    - **Описание**: Зависимости продиктованые бизнес-логикой. Это другие сервис-компоненты реализующие узкую доменную область и необходимые как вспомогательные сущности в реализации большей логики.
    - **Внутренний приоритет категории**: не важен
        - экземпляр сервис-компонента реализующий внутри себя логику сборки SQL-запроса
        - экземпляр сервис-компонента реализующий внутри себя исполения и обработки SQL-запроса
        - экземпляр клиента к удаленным API, внешним относительно проекта
        - и тому подобное ...

### Правила

1. Важен порядок передаваемых аргументов:
    1. Нулевой приоритет: экзепляр контекста - `ctx context.Context`. Стандартно не передаем, но если необходим, то он впереди всех.
    1. Первый приоритет: "служебные" зависимости - экземпляры конфигов, логгеры, и тому подобное.
    1. Второй приоритет: - инфраструктурые зависимости - экземпляр клиента базы данных, клиент к redis, http или gRPC клиенты, и тому подобное
    1. Третий приоритет: логические зависимости для работы бизнес-логики - 
    1. Приоритет передачи:
        - экземпляр форматтера ошибок (если необходим)
        - экземпляр логгера (если необходим)
        - экземпляр сервис-компонента конфигурации (если необходим)
        - экземпляр трассироващика (если необходим, и если передается как отдельный сервис-компонент)
1. Каждый параметр на отдельной строке. Здесь действует общее правило на оформление любой функции:
    - Если у функции больше 1 параметра - каждый параметр на новой строке
1. Категории зависимостей отделяем пустой строкой. Правило применяет для:
    - Описания Go-структуры сервис-компонента
    - Описания factory-функции при передаче параметров
    - Создании экземпляра Go-структуры
1. Обязательная проверка на `nil`. Задача "factory-функции" - не пропустить пустую зависимость что бы исключить панику(go panic) при работе сервис-компонента
1. Возвращаем всегда указатель на экземпляр структуры
1. Паредаваемые зависимости в factory-функцию должны имплементировать определенный на уровне пакета интерфейс
1. Стадия инициализации на `Init(ctx context.Context) error`
1. Стадия запуска на `Run(ctx context.Context) error`
1. Завершение работы обязательно по завершению работы (отмены) контекста ранее передаваемого в `Run(ctx context.Context) error`
1. Мониторинг состояния внутри сервис-компонента, но сохранение в другой. Если сервис-компонент содержит параметры состояния применимые к метрикам или отчету о состоянии приложения, то для их опроса необходимо:
    - Использовать возможности библиотеки `bc-wallet-common-lib-healthcheck`
    - Использовать для сохранения состояния промежуточный сервис-компонент (подробнее в `bc-wallet-common-lib-healthcheck`)

### Пример

Пример реализации функции которой не нужен контекст, но нужны "служебные" или "базовые" зависомсти, а так же одна "бизнес" зависимость.

```go

var ErrMissingSvcDependencies = errors.New("missing service-componenct dependency")

type httpUserPermissionsHandler struct {
    l *slog.Logger                  // Правило для экономии длины строк в коде - "l" для logger
	e errorFormatterService         // Правило для экономии длины строк в коде - "e" для error-formatter
    cfgSvc configService

    redisConn *redis.Connection

    userRepoReaderSvs userRepoReaderService
    userRepoWriterSvs userRepoWriterService
}

func NewHTTPHealthCheckerService(                   // Первая строка пустая всегда
	errFmtSvc errorFormatterService,                // Третий приоритет за сервис-компонентом "форматтером" ошибок
    logFactorySvc loggerBuilderService,             // Второй приоритет за сервис-компонентом "создателем" логов
    cfgSvc configService,                           // Первый приоритет за сервис-компонентом конфигурации
    // Пустая строка отделяет категории зависимостей - далее идут инфраструктурные зависимости
    redisConnection *redis.Connection,              // Здесь начинается приоритет инфраструктурных зависимостей
    // Пустая строка отделяет категории зависимостей - далее идут логические зависмости
    userRepoReaderSvs userRepoReaderService,
    userRepoWriterSvs userRepoWriterService
) *httpHealthChecker {
    if errFmtSvc == nil { // Обязательная проверка на nil каждой зависимости
        return fmt.Errorf("health checker: %w: %s", 
            ErrMissingSvcDependencies, "missing error-formatter service component") // Ситуация когда доспустимо использовать fmt для форматирования ошибки, в остальных случаях `lib-errors`
    }

    if logFactorySvc == nil { // Обязательная проверка на nil каждой зависимости
        return errFmtSvc.Error(ErrMissingSvcDependencies, "missing logger builder service component") // здесь уже для форматирования используем error-formatter
    }

    if cfgSvc == nil { // Обязательная проверка на nil каждой зависимости
        return errFmtSvc.Error(ErrMissingSvcDependencies, "missing config service component") // здесь уже для форматирования используем error-formatter
    }

    if redisConnection == nil { // Обязательная проверка на nil каждой зависимости
        return errFmtSvc.Error(ErrMissingSvcDependencies, "missing redis connection") // здесь уже для форматирования используем error-formatter
    }

    if userRepoReaderSvs == nil { // Обязательная проверка на nil каждой зависимости
        return errFmtSvc.Error(ErrMissingSvcDependencies, "missing data repository reader service component")
    }

    if userRepoReaderSvs == nil { // Обязательная проверка на nil каждой зависимости
        return errFmtSvc.Error(ErrMissingSvcDependencies, "missing data repository reader service component")
    }

    return &httpHealthChecker{ // всегда возвращаем указатель на структу, исключение для паттерна "Простая фабрика / Фабричный метод
		l: logFactorySvc.NewSlogNamedLoggerEntry("healthcheck"),
		e: errFmtSvc,
        // Пустая строка отделяет категории зависимостей - далее идут инфраструктурные зависимости
        redisConn: redisConnection,
        // Пустая строка отделяет категории зависимостей - далее идут логические зависмости
        userRepoReaderSvs: userRepoReaderService,
        userRepoWriterSvs: userRepoWriterService
	}
}
```
