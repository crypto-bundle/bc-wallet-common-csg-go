# Слой данных. Правила написания кода

---
**Цель**: Определить правила реализации слоя доступа к данным
**Категория правил**: App Development, data layer
**Краткое содержание:** Правила слоёв данных — PostgreSQL и Redis, repository pattern, interfaces
---
## Введение

В данном документе описаны правила и рекомендации по организации кода приложения в контексте _слоя данных_.
Под термином `слой данных` подразумевается код реализующий набор сервис-компонентов отвественный
за общение с различными внешними сервисами хранения данных.

Стандартными сервисами хранения данных в проекте являются:
- `PostgreSQL` - персистентная SQL-подобная база данных
- `Redis` - кеширующая NoSQL база данных

## Правила

По сути все правила сводятся к нескольким пунктам:
- Для каждого из типа хранилищ своя библиотека хелпер
  - `PostgreSQL` - [bc-wallet-common-lib-postres](https://github.com/crypto-bundle/bc-wallet-common-lib-postgres)
  - `Redis` - [bc-wallet-common-lib-redis](https://github.com/crypto-bundle/bc-wallet-common-lib-redis)
- Для работы с сущностей внутри хранилищ данных создаются отдельные пакеты и отдельные сервис-компоненты.
- Все ошибки пораждаемые внутри пакета должны быть обернуты через 
  error-formatter библиотеку - [bc-wallet-common-lib-errors](https://github.com/crypto-bundle/bc-wallet-common-lib-errors).
  При форматировании ошибок важно использовать возможность библиотеки `bc-wallet-common-lib-errors` 
  по создания ошибок с указанием имени _скоупа_ - сфера источника ошибки. Для этого нужно использовать
  форматтер ошибок как сервис-компонент удовлетворяющий зависимости, а именно `ScopedErrorFormatter`.
- Некоторые из возникаемых на уровне слоя данных ошибок могут иметь свой [статус-код ошибки](./4_go_app_errors_status_codes.md),
  здесь на усмотрение и отвественность разработчика.

### PostgreSQL

Важно отметить что в проекте принята парадигами что для общения с базой данных и различным таблицами
внутри нее рекомендуется писать отдельный сервис-компонент в отдельном Go-пакете.
Разбиения слоя данных на разные пакеты и сервис-компоненты ведется по принципу родства таблиц и моделей данных.

В качестве примера рассмотрим следующие варианты:
- Для родственных таблиц `events`, `events_data` допустимо создать отдельный сервис-компонент в пакете `events_data`.
- Предположим что таблица `processing_operations` независима от прочих таблицы, для нее нужно создать
  отдельный пакет `processing_operations_data` и отдельный сервис-компонент.

Описанные выше примеры в первую очередь руководствуются очевидной логикой. 
По факту разбиение слоя даных на разные сервис-компоненты и пакеты может быть
не настолько очевидным, в таком случае принятие решения ложиться на конкретного
разработчика.

Процесс написания кода реализующий логику общения с SQL-базой данных **PostgreSQL**
должен сопровождаться использованием библиотеки `bc-wallet-common-lib-postres`. Подробнее
про работу с этой библиотекой описано в репозитории [bc-wallet-common-lib-postres](https://github.com/crypto-bundle/bc-wallet-common-lib-postgres),
а так же в документе [Работа с PostgreSQL](./4_go_app_postgresql.md).

Данная библиотека создана для двух основных целей:
- Унификация конфигурации подлючения целевого приложения к базе данных **PostgreSQL**.
- Менеджмент подключения к базе данных.
- Добавление функций-помощников для работы с транзакционным стейтментом.

### Redis

Как и с персистентными хранилищами при работе по написанию кода коммуникации с Redis введена парадигма
**_родственные модели данных в отдельном сервис-компоненте и пакете_**.

По факту разбиение слоя данных для кеширующего хранилища на разные сервис-компоненты и пакеты может быть
продиктована разными мотивами, которые не всегда можно четко формализовать. В таком случае принятие решения
ложиться на конкретного разработчика.

Процесс написания кода реализующий логику общения с NoSQL кеширующей базой данных **Redis**
должен использовать в качестве основного инструмента библиотеку [go-redis](github.com/go-redis/redis/v8).
Библиотека `bc-wallet-common-lib-redis` используется только для следующих целей:
- Унификация конфигурации подлючения целевого приложения к кеширующему хранилищу **Redis**.
- Менеджмент подключения к **Redis**.
Подробнее про работу с этой библиотекой описано в репозитории [bc-wallet-common-lib-redis](https://github.com/crypto-bundle/bc-wallet-common-lib-redis).
