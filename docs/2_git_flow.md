# Работа с Git для разработчиков команды GreenPay crypto acquiring

# Цели

- чистая `master` ветка, без технических коммитов
- ясное указание на занятость `develop` под новый релиз
- история релизов в git (IDE friendly) и в github
- связность релизов по разным репозиториям (общие имена и версии)
- обновления до стабильных версий из `master`, не из `develop`
- зафиксировать правила по описаниям коммитов

# Аббревиату́ры

- CR - code review
- PR - pull request
- GPAYGF - GreenPay Git flow

# Терминология

## Тестовый стенд
- для тестирования приложений из ветки `development`

## Релизный стенд
- после тестирования приложений на тестовом стенде если к приложениям нет вопросов - 
  приложение выкатывается на релизный стенд 
- для разработчика это требует мерж `development` в `master`
- общий тест в `development` может содержать несколько фич, тестируемых
  одновременно, для выката единым релизом
- для ускорения релизов предпочтительно тестирование и выкат одной
  фичи из `development` в `master`

## Отладочные коммиты
В отличие от регулярных коммитов, отладочные -- это временные правки
для тестов локально или на юнитовой среде. Этих правок не должно быть
в продакшне. Как примеры:
- добавление временных логов
- добавление тегов в трассировщик
- внесение отладочной логики

Такие коммиты должны пропадать при слиянии изменений из:
- фича-ветки в `development`
- из `development` в master

Как основной способ избавить от таких коммитов - merge + squash 

## Ветка задачи
- задачная ветка создается разработчиком в начале работы над задачей
- задачная ветка именуется в смешанном кейсе с разделением "-" по номеру
  задачи. Тег и название задачи в `UPPERCASE`, краткое доп описание в `lowercase`.
  Например для задача GPAY-123: **GPAY-123**.
  Опционально с описанием **GPAY-123-the-description**
- ветку создаёт разработчик как форк от `development` ветки в начале
  работы над задачей

# Коммиты и теги

## Коммит-сообщения

### Обычные коммиты
- Описания коммита строго на английском
- Формулировки в коммит-сообщение исключительно в **прошедшем времени**, как фиксация **свершившегося события**
  используем базово такие слова как - `Fixed`, `Added`, `Changed`
- **Избегаем** неинформативных коммит-сообщений, например:
  - `fix(GPAY-123): Fixed`
  - `fix(GPAY-123): Some fixes`
  - `fix(GPAY-123): Small fixes`
  - `feat(GPAY-123): Added task logic`
  - `chore(GPAY-123): Refactoring`
- Коммит-сообщение должно содержать:
  - Префикс в виде характера коммита, например
    - `feat` - feature - коммит добавлен для реализации какого либо нового функионала
    - `chore` - коммит добавлен как "домашняя работа" или внутрення работа над репозиторием, 
      не привязан к какой либо бизнес-фиче или бизнес-логике 
    - `fix` - коммит добавлен как исправление неверно работающего функционала
    - `style` - коммит добавлен как исправление для соответсвия общему стилю кода
    - `docs` - коммит добавлен как внесение изменений в документацию внутри репозитория
    - `debug` - коммит добавлен для внесения в приложение отладочной информации
  - После должно следовать обрамленное в круглые скобки Тег-задачи или ее код из таск-текера
  - После описание содержимого коммита в доступном виде для беглого понимания

Например
```
feat(GPAY-123)Add new handler for handling unhandled requests
fix(GPAY-123): Fixed bug in NATS message processing at witdraw stage 
```
- длина описания до 78 символов
- коммит может содержать расширеное описание. Пример:
```
feat(GPAY-123)Removed new handler

It could head reason why we remove these handlers.
It could be split to several lines.
```

### Отладочные коммиты
- формат описания не регламентирован
- для того, чтобы не пропустить случайно отладочные коммиты в
  `development` ветку, рекомендуется их формат делать сильно отличающимся от
  регулярных коммитов:
```
debug[GPAY-123]DEBUG COMMIT.ADDED LOGS
```

## Подпись коммитов и тегов

### Причины внедрения

Основной причиной данного требования является необходимость подтверждения авторства 
вносимых разработчиками изменений в git.

### Описание

Все изменения от разработчиков должны быть подписаны через механизм электронной цифровой подписи.
Рекомендуемый инструмент - `GNU Privacy Guard`, он же `GPG`.
Бзовый принцип сводится к тому что разработчик подписывает каждое вносимое в репозиторий изменение
своим приватным ключем, а публичный вносит в список GPG-ключей на платформе GitHub. 
Впоследствии через публичный ключ возможно проверить соответствии подписи.

### Настройка

Подробнее про настройку можно почитать:
- https://docs.github.com/en/authentication/managing-commit-signature-verification/telling-git-about-your-signing-key
- https://docs.github.com/en/authentication/managing-commit-signature-verification/generating-a-new-gpg-key

# Использование GPAY git-flow

## Резработчка и тестирование на тестовом стенде

1. Разработчик создает ветку для задачи от `master`.
1. Далее после локальной отладки делаются пуши в эти задачные ветки.
1. Ветки задач мержатся в `development` через PR с _rebase_, для
   прямолинейности коммитов.
1. Здесь точка CR: Согласие на слияние ветки задачи должно быть получено 
   как минимум от одного другого разработчика.
1. По согласованию между разрабочиками работающими над репозиторием в `development`
   можно влить несколько фич одновременно которые планируется передать в релиз.
1. При необходимости напрямую в `development` вносятся отладочные
   коммиты и в принципе любые правки, но следует помнить, коммиты из этой ветки
   позже будут собраны в `release` ветку, а `development` ветка возможо будет пересоздана из `master`.
1. Если в результате тестов требуются новые правки логики
   (например rejected by QA), то снова создается задачная ветка от
   `development` и вносятся правки вновь через PR с CR и _rebase_'ом.

На всё время разработки фичи её код хранится в ветках задач,
ветки не удаляются при мержах в `develop`!

Интеграционные ветки и ветки задач никогда не обновляются из
`release-*` и `develop` веток!

## Предрелизное тестирование

1. Все коммиты готовящиеся к релизу должны быть собраны в отдельной `release`ветке.
   Название `release` ветки заполняется в соотвествии с общими принципами, 
   но с префиксом `RELEASE-` в имени ветки. Например - `RELEASE-GPAY-123-some-text`.
   Ветка может быть создана как форк от текущей `master` ветки.
   Добавить коммиты в ветку можно как через MR или через cherry-pick.
1. Уведомление о релизе на данном шаге не требуется.
1. Все release-ветки автоматически будут выолжены на отдельный пред-релизный стенд.
1. Release-стенд блокируется для каких либо других правок на целевой репозиторий, 
   только те что согласованы к релизу. 

Ветка юнита `release99` никогда не мержится в `develop`!

Аннотация (git note) ставится на все коммиты попадающие в `develop`,
это отражает принадлежность коммитов к релизам!

## Release to production

1. PR из `release` в `master` строго без rebase и squash.
1. Для отката релиза делается revert `master` полный или частичный.
1. Аннотация к релизу включает в себя ранее предоставленное описание релиза
1. Финально, на последний merge-коммит проставляется релизный аннотированный тег
    **vx.y[.z]-<date>[-desc]** (например **v1.2-211212-ibans**)
    ```bash
    git tag -a -m "Release notes"
    ```
1. Делается мерж `release` ветки в `master`, строго без rebase и squash.
1. Далее выкат.

Полный откат релиза это revert всех коммитов найденных по их notes в
`develop` и `master`.

# Хот-фиксы

Хотфикс это релиз с отличиями от утвержденного порядка
релизов. Примеры таких отличий, при которых релиз следует трактовать
как хотфикс:

- требуется пропустить тесты на площадке или общий тест
- надо сразу задеплоить фикс в продакшн, минуя тестовые ветки
- выкат без утвержденных чеклистов

В принципе любую задачу можно выкатить как хотфикс. Очевидно, что для
пропуска любых шагов утвержденного флоу релизов требуется обоснование
&#x2013; срочное решение проблемы, когда прогон задачи по полному флоу
затянет решение надолго и это приведет к потере денег или репутации
компании.

На хотфикс заводится отдельная ветки, все PR и апрувы в ней.

- ветка как правило именуется `HOTFIX-GPAY-123`
- в принципе, пока можно именовать как угодно, но скрипты билда и деплоя
  будут ориентироваться на префикс `HOTFIX-`
- все коммиты в рамках хотфикс должны быть с префиксом `fix` в 
  тексте коммита - `fix(GPAY-123): Fixed bug in withdraw processing flow`.

# Коммиты для документирования

Правки документации (README) или опечаток в комментариях, т.е. не
затрагивающие явно код сервиса - могут иметь упрощенный флоу, с
коммитами сразу в `develop` и `master` минуя задачные или
интеграционные ветки.


# Приложение. Пояснения по выбору решений

## Пояснения к решениям с тегами

- github использует свою схему хранения релизов, без использование аннотированных тегов и заметок

<https://stackoverflow.com/questions/29010880/are-github-release-notes-store-on-git>

- нам удобно использовать механику аннотированных тегов, поскольку она
  не привязана к github и позволит видеть release notes локально в git
  client
- это дублирование действий потребует автоматизации, но в результате
  получаем идентичный просмотр релизов через вебинтерфейс github.com и
  через локальный git log


## Мотивация release веток

- отделить технические коммиты в рамках разработки и отладки фичи
- одностроенне движение коммитов от ветки задачи к master ветке.
- релиз какой либо фичи или задачи может быть разбит на несколько веток, 
  но в итоге будет сведен в одну `release` ветку
  далее в develop подразумевается, что задачи должны тестироваться и
  релизиться вместе
- в develop могут накапливаться задачи по разным фичам к релизу, мерж
  всей `development` ветки в `master` может привести к проблемам.
- `release` ветки могут инкапсулировать логику фичи из нескольких задач
