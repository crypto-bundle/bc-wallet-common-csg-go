# Правила ведения документации к приложению

## Введение

Документация уровня конкретного приложения должна включить в себя следующий минимум:
- Описание цели приложения
- Описание коммуникационных возможностей приложения
- Описание способа сборки приложения
- Описание способа запуска приложения
- Описание уникальных для приложения конфигурационных параметров
- Описание инфраструктурных зависимостей
  - Используемые перситентные базы данных - название сервера, название конкретной базы данных. 
  - Используемые кеширующие базы данных - название сервера, название конкретного бакета.
  - Используемые брокеры сообщений - название сервера, название стримов, топиков и прочего.
  - Используемое пространство в _**HashiCorp Vault**_

Опционально могут быть задокументированы:
- Особенности процессинга внутри приложения
- Подробное описание моделей данных приложения
- Детализированное описание с визуализацией какого-либо сложного механизма процессинга набора событий
- Особенности деплоймента через Kubernetes и Helm

### Правила

Фактически правила написания документации сводятся к трем простым пунктам:
- Минимальные требования к доументации должны быть описаны в `README.md` файле.
- Структура контента минимально-необходимой документаций должна следовать следующему шаблону:
  - Описание приложения
  - Краткое описание способов взаимодействия с прилоежением - http/gRPC/queue-processing
  - Описание способов сборки приложения
  - Описание способов запуска приложения
  - Инфраструктурные зависимости
  - Описание уникальных для приложения конфигурационных параметров:
    - ENV-переменные
    - Поля в json или yaml файлах
  - Информация о лицензировании кода
- Опциональная документация может быть описана в отдельной директории `docs` в виде одного или нескольких файлов.
- Файлы опциональной документация оформляются в `Markdown` синтаксисе.
- Структура контента опциональной документация остается на выбор разработчика.
